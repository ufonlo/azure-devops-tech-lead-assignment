# CTO summary

This proposal moves the API to Azure using a deliberately small managed platform: Azure Container Apps, Container Registry, Key Vault and Log Analytics. Terraform defines one reusable platform module, while development and production retain separate state, identities and lifecycle. This provides consistency without allowing a development change or credential to silently cross into production. The current Free Trial permits only one Container Apps managed environment globally, so development serves the API while production intentionally provisions only its supporting platform resources.

GitHub Actions uses Azure workload identity federation, so the company stores no long-lived cloud credential in GitHub. Every infrastructure pull request is formatted, validated and security-scanned, and updates separate development and production plan comments for review before merge. A protected-main run applies the exact saved development plan and then prepares production. Production verifies the saved plan checksum and requires human approval through a protected GitHub environment before applying it. That pipeline runs end to end today, but production serves no traffic until it moves to the target separate subscription and enables its Container Apps runtime.

Container Apps is preferred over AKS for the first stage because the current requirement is a containerized API, not a Kubernetes platform. It gives managed ingress, revisions, autoscaling and scale-to-zero while reducing cost and operational burden for a small team. The design preserves a migration path to AKS if Kubernetes-specific needs emerge.

The main residual risks are bootstrap privilege, public endpoints, untested application health behavior and incomplete disaster-recovery requirements. The next increments are immutable image promotion, smoke tests, alerting, private networking where justified, and a rollback game day. AI may accelerate drafting, but deterministic validation, human plan review and explicit data-handling rules remain mandatory.
